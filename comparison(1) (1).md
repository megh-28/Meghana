# Lab 2 · Scratch vs Copilot-after-fixes Comparison

| Aspect | Scratch (`LibraryBook`) | Copilot-after-fixes (`LibraryBookAI`) |
|---|---|---|
| **Encapsulation** | All four fields are private from the start: `private final String author;`, `private final String title;`, `private final String isbn;`, and `private boolean isAvailable;`. The identity fields are also `final`, and the class exposes getters but no setters. | All fields are private: `private final String title;`, `private final String author;`, `private final String isbn;`, and `private AtomicBoolean available;`. The three identity fields are `final`; however, the `available` reference itself is not declared `final`, even though it is only initialized in the constructor. |
| **Validation** | The constructor explicitly checks every required value for both `null` and blank input, for example `if(author==null||author.isBlank())` and the equivalent checks for `title` and `isbn`. Invalid input throws `IllegalArgumentException`. | Validation is centralized in `validateRequiredText(String value, String fieldName)`. It checks `value == null`, then trims the input with `String trimmed = value.trim();` and rejects `trimmed.isEmpty()`. This also normalizes valid input by storing the trimmed value, which the scratch version does not do. |
| **Exception handling** | Constructor validation uses `IllegalArgumentException`, while invalid object-state operations in `checkOut()` and `returnBook()` use `IllegalStateException`. For example, `checkOut()` throws `new IllegalStateException("Book already in use")` when `!isAvailable`. | The exception types match the cause of failure: `validateRequiredText()` throws `IllegalArgumentException` for invalid constructor arguments, while `checkOut()` and `returnBook()` throw `IllegalStateException` when the requested transition is invalid. Messages such as `"Book is already checked out"` and `"Book is already available"` also describe the failed state clearly. |
| **State guards** | `checkOut()` prevents a second checkout with `if(!isAvailable)`, and `returnBook()` prevents returning an already available book with `if(isAvailable)`. The state is changed only after the guard passes: `isAvailable=false;` or `isAvailable=true;`. | `checkOut()` uses `available.compareAndSet(true, false)` and `returnBook()` uses `available.compareAndSet(false, true)`. A failed comparison throws `IllegalStateException`, so double checkout and double return are prevented atomically. |
| **Specification drift** | The scratch implementation stays close to the requested model: three text fields, one boolean availability field, constructor validation, state-changing methods, and getters. It does not introduce helpers, concurrency types, trimming, or extra public methods. | The implementation adds `AtomicBoolean`, atomic compare-and-set behaviour, input trimming in `validateRequiredText()`, and Javadoc describing thread-safe behaviour. These are reasonable enhancements, but thread safety and automatic whitespace normalization were not explicitly required by the specification. |
| **Code quality** | Method and field names such as `checkOut()`, `returnBook()`, and `isAvailable` are understandable, and the control flow is simple. Formatting is less polished in places, for example `public  String getIsbn()` has an extra space and the constructor parameters lack spaces after commas. The message `"book is returned and is available"` is also less precise than `"Book is already available"`. | Repeated validation is removed through `validateRequiredText()`, formatting and naming are consistent, and exception messages are clearer. The `compareAndSet()` calls make the state transitions concise, although `AtomicBoolean` increases complexity compared with the simple boolean required for this class. |

## Verdict

I would hand the **Copilot-after-fixes version** to a teammate because its validation is centralized, its exception messages are clearer, and its formatting is more consistent. However, I would simplify `AtomicBoolean` back to a normal boolean unless thread safety is an explicit requirement, because it adds behaviour and complexity beyond the specification. The scratch version meets the core requirements well but would benefit from cleaner formatting, a reusable validation helper, and clearer exception messages. Next time, the C-I-E prompt should explicitly say to **follow only the requested specification, avoid unrequested concurrency or normalization behaviour, centralize repeated validation, use `IllegalArgumentException` for invalid inputs and `IllegalStateException` for invalid state transitions, and keep the implementation minimal and consistently formatted**.
